# Architecture

```
cmd/taskglass        entry point: flags, single instance, logging
internal/app         tray menu + main loop (ties everything together)
internal/config      schema, defaults, validation, atomic save   (portable)
internal/state       pure rule resolution: context -> appearance  (portable)
internal/taskbar     applies appearances per taskbar, restores
internal/winapi      the only package that calls Win32
internal/autostart   HKCU Run key
assets/              embedded tray icon (generated by tools/genicon)
```

## How the effect works

Explorer's taskbar windows (`Shell_TrayWnd` for the primary monitor, `Shell_SecondaryTrayWnd` for the others) accept an accent policy through the undocumented `user32!SetWindowCompositionAttribute` (attribute 19). TaskGlass sets that policy (gradient, transparent gradient, blur-behind or acrylic with an `0xAABBGGRR` tint). Disabling the policy and sending `WM_DWMCOMPOSITIONCHANGED` makes Explorer repaint the stock look.

## Main loop

Every `poll_ms` the loop, from a single goroutine:

1. finds all taskbars (so new monitors and Explorer restarts are handled for free; vanished handles are dropped),
2. enumerates top-level windows once to collect monitors that show a maximized, visible, non-cloaked, non-tool window,
3. checks whether the foreground window is the Start/Search host (`Windows.UI.Core.CoreWindow` owned by `StartMenuExperienceHost`/`SearchHost`/`SearchApp`),
4. resolves each taskbar's appearance with `state.Resolve` and applies it if it changed or `refresh_ms` elapsed,
5. every second, hot-reloads the config if its mtime changed.

On exit the loop calls `Restore`, which resets every taskbar. `taskglass --restore` does the same from a fresh process if the app was killed.

## Design choices

- **Go without cgo**: `golang.org/x/sys/windows` plus lazy DLL procs; one static binary, trivial CI.
- **Pure logic isolated** in `config` and `state` so it is tested on any OS; Win32 code is behind `_windows` build tags.
- **Fail soft**: invalid config keeps the previous settings; apply errors are logged and retried.
- **Polling over hooks**: a 100 ms sample of a handful of cheap calls is simpler and more robust than a WinEvent hook; a hook-based wake-up is a possible future optimisation.
